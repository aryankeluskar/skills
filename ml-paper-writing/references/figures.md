# Figures

Contents: three kinds of figure · storyboarding · lessons from sketch to final · teaser figures · typography · color · layout · visual hierarchy · sizing and export · tools · plot checklist

## Three kinds of figure

| Kind | Job | Typical tool |
|---|---|---|
| Teaser / illustration (often Figure 1) | The elevator pitch: what a reader who never reads the paper should take away | Figma, Illustrator, draw.io, PowerPoint/Keynote; sometimes code + manual polish |
| Framework / method diagram | A self-explanatory blueprint of the approach that highlights what is new | draw.io, Visio, Figma, TikZ |
| Results | Directly support a claim. Every bar, curve and point should reinforce the argument; mark baselines; make the comparison effortless | matplotlib / seaborn, generated by code for reproducibility |

Every figure should have a clear answer to "why does this figure exist, and what should the reader take away?" Cut decorative plots that add no insight.

## Storyboarding

Sketching figures before (or while) running experiments turns intuitions into falsifiable predictions and keeps the visual narrative coherent. It suits phenomenon-driven empirical work especially well; adapt for other kinds of projects.

For each planned figure, write a spec:

```
Figure N: <working title>
Message:          the one sentence a reader should take away
Hypothesis:       the pattern you expect to see
Falsifier:        what result would contradict it, and what you would conclude then
Comparison:       which conditions are compared; which comparison matters most
Encoding:         x = ..., y = ..., color = condition, panels = ...
Panel order:      follows the explanation (mechanism before application, etc.)
Data needed:      experiment, models, n / seeds
Status:           sketch | preliminary | final
```

Order the specs so the figures alone tell the paper's story (Fig 1 teaser, then evidence in the order of the claims). A reader flipping only through figures and captions should get the narrative.

At the planning stage, stop at message, hypothesis, comparison and encoding. Fonts, exact widths and styling are decided when the figure is made; including them in a story document only adds length.

When a result comes in, compare it with the spec's hypothesis. A mismatch is information: it often calls for a new condition that separates two explanations, rather than a redesign that hides the mismatch.

## Lessons from sketch to final

From the token-cue paper's figure revisions, generalized:

- **One idea per plot.** A sketch showed both pass@1 and pass@16. The figure's message was about single-attempt accuracy, so pass@16, which answers a different question, was dropped.
- **Panel order follows the explanation, and the explanation can change.** A three-panel figure originally led with training efficiency (the application). Once the paper's focus became understanding, panels were reordered to go from where the models differ, to which openings became more likely, to what that means for training efficiency. Simple bars were also replaced with branching diagrams that showed the actual token sequences and their probabilities.
- **Choose the axis of variation that shows the comparison you care about.** Training curves showed cue effects emerging over time, but the real comparison was between cues under each data edit, so grouped bars replaced the curves.
- **Unexpected results can improve the experiment.** The prediction was that replacing "Okay" with "Chicken" in training data would make "Chicken" work and "Okay" stop working. Only the first half held. A second data edit was added to redirect "Okay", and the final figure contrasted creating a new cue with redirecting an old one.
- **A vague sketch can define the measurement.** A loose "flow" picture linking cues to data sources had no method behind it at first; aiming for that picture led to comparing model representations during generation with those on training documents.
- **If a figure does not speak for itself**, ask whether the experiment can be simplified or the result shown more directly, rather than adding explanation.

## Teaser figures

The teaser distills the whole paper into one view. Heuristic: if someone will never read the paper, what should this figure leave them understanding?

- Make it after the main results exist, so it depicts what was actually found.
- Find the single mental picture. Close your eyes and imagine explaining the paper with one chalkboard drawing.
- If one model explains several effects, show them in one unified diagram instead of separate panels (e.g. a branching tree of opening tokens, where RL thickens the good branch and a data edit turns a rarely taken branch into a reasoning branch).
- Pair the concept diagram with a small strip of headline numbers, so the idea is anchored in evidence.
- It should catch the eye as the lead image of a social-media thread, but avoid overloading it with detail; its job is to attract and orient, not to explain every step.
- Iterate. Expect several versions.

## Typography

- Choose fonts deliberately rather than accepting plotting defaults; it gives the paper a coherent look.
- Use a sans-serif for figure labels so they stand apart from the (usually serif) body text. Use font weight (light vs. regular vs. semibold) for emphasis instead of more colors.
- Use monospace for literal strings: tokens, code, prompts, model outputs.
- Free choices: Inter, Source Sans 3, IBM Plex Sans, Helvetica/Arial (sans); B612 Mono, JetBrains Mono, IBM Plex Mono (mono). The source paper used Graphik (commercial) and B612 Mono.
- Size text for the final printed size: about 7 to 9 pt at the width it will appear. Design the figure at that physical width rather than shrinking a large figure.

## Color

- **Use one palette with numbered shades** (light to dark) across all figures. Tailwind v4's palette, which is defined in the perceptual OKLCH space, works well and is built into `scripts/paper_style.py` as hex values.
- **One hue per condition, everywhere.** For example: neutral gray = baseline / no intervention, amber = the method or cue, blue = RL model, red = the counterfactual condition. Readers then recognize conditions without rereading legends.
- **Same shade level for comparable elements.** For example, 400-level fills with 600-level outlines for all bars (`ps.fill_edge("amber")`).
- **Use well-separated hues for categories.** Hues that are too close (several blues) make conditions hard to tell apart. But do not use more colors than there are concepts: one figure with eight colors is hard to read.
- **Colorblind safety.** About 4% of people (mostly men) have red-green color blindness. Never let red vs. green alone carry key information; vary lightness too, or use blue vs. orange/amber.
- **Lightness carries emphasis; hue carries identity.** Many readers print in greyscale or cannot separate hues. The emphasized condition should be clearly darker (or clearly lighter) than everything around it, not just a different hue. Light amber next to light blue and light gray reads as three near-identical grays. Check with the greyscale preview from `ps.save()`, or compare `ps.lightness(hex)` values (CIE L*, 0 to 100): aim for at least about 15 points between the key condition and its neighbors. A reliable pattern is a strong shade for the method (L* around 45 to 60, e.g. blue-600, orange-600, amber-600) against light baselines (L* 80 or more, e.g. 200 to 300 shades or light grays). Yellows and ambers are light even at mid shades (amber-400 is about L* 80), so go to 600 when they carry emphasis.
- **Colormaps for numeric values.** Sequential (e.g. viridis, or white-to-dark single hue) for ordered quantities starting from zero; diverging (e.g. RdBu, neutral at center) when there is a meaningful midpoint such as zero change from baseline. Prefer perceptually uniform maps so small differences do not look large. Center diverging maps on the true midpoint (`TwoSlopeNorm` / `CenteredNorm`).
- Defaults from seaborn or draw.io are acceptable when tuned for readability; look at figures in recent papers at the target venue and in journals like Nature for restrained, effective color use.

## Layout

- Order conditions as the argument runs: no-intervention baseline, then alternatives from weakest to strongest, then the method. Do not let pandas sort them alphabetically.
- Whitespace creates grouping. Tighter gaps within a row and larger gaps between rows make readers compare along rows, and vice versa. Decide which comparison you want and space accordingly.
- Put compared panels on shared axes with identical scales, adjacent to each other.
- Align panel edges and baselines; use consistent panel sizes.
- Label panels (a), (b), (c) when the text refers to them.

## Visual hierarchy

What is largest, darkest, most saturated or thickest gets looked at first. Decide what deserves attention:

- The key series: saturated color, thicker line, larger markers, drawn on top (`zorder`).
- Context series: light gray or low alpha, thin lines.
- Annotate the key point directly (a label at the line end, an arrow, the delta written on the plot) instead of relying only on a legend.
- Check whether what stands out is what you intended. Large markers emphasize individual samples and their deviation from a trend; a heavy fit line emphasizes the trend.
- Make small but important differences visible. If the claim is "costs less than one point of MMLU", a raw 0 to 80 axis hides the cost entirely, while an auto-zoomed axis exaggerates it. Plot the change from baseline on a fixed, sensibly bounded axis, or annotate the delta.
- With few seeds (n of 3 to 5), show the individual seed values as points over the bar, or state what the error bars are. If a metric has zero variance across seeds, say why (deterministic eval?), rather than drawing error bars of zero.
- Remove clutter: top and right spines, heavy gridlines, redundant tick labels, boxed legends.

## Sizing and export

- Design at final width. Typical widths (check your template with `\the\columnwidth` and `\the\textwidth`):

| Venue | Column | Full text width |
|---|---|---|
| NeurIPS, ICLR (single column) | n/a | 5.5 in |
| ICML (two column) | 3.25 in | 6.75 in |
| ACL / EMNLP / NAACL | 3.03 in | 6.30 in |
| CVPR / ICCV | 3.25 in | 6.875 in |

- Export vector formats (PDF, or SVG for further editing) with text kept as text: crisp at any zoom, and readers can select and search labels. In matplotlib set `pdf.fonttype = 42` so fonts embed as TrueType rather than Type 3, which some venues reject. `paper_style.use_paper_style()` does this.
- Never use JPEG for plots or diagrams. Use PNG only for genuinely raster content (photos, generated images), at 300 dpi or more.
- PowerPoint/Excel exports risk rasterization; export to PDF and check.
- If the final paper PDF is compressed, use settings that keep vectors and fonts, or figures get downsampled.
- Use fonts installed as `.ttf`. Matplotlib cannot embed `.otf` (CFF) fonts as TrueType, and the resulting PDF has a font-type mismatch some checkers reject. `use_paper_style()` skips `.otf`-only fonts automatically.
- `paper_style.save()` writes a PDF, a color PNG and a greyscale PNG preview. It warns about Type 3 fonts, mis-embedded `.otf` fonts (when `pdffonts` is installed) and embedded raster images.

## Tools

| Tool | Strengths | Weaknesses |
|---|---|---|
| matplotlib / seaborn | Reproducible, precise, vector output; regenerate when results change | Fine manual tweaks mean editing code |
| draw.io | Free, collaborative, vector export with auto-crop | Manual styling, limited shapes |
| PowerPoint / Keynote / Excel | Fast, familiar, alignment helpers | Limited styling; export may rasterize |
| Visio | Precise technical diagrams, math notation, vector | Paid; manual styling |
| Figma / Illustrator | Polished teasers and diagrams | Manual; not tied to data |
| TikZ | Typographically matched to the paper | Slow to write and iterate |

Community styles differ: ML venues favor abstract, minimal figures; NLP venues often use concept- and flow-based diagrams; data-mining venues favor detailed modular pipelines. Look at recent accepted papers at the target venue.

## Plot checklist

- [ ] The figure's one-sentence message is written down, and the plot shows exactly that.
- [ ] The most important comparison is adjacent, on shared axes.
- [ ] Each condition has the same color as in every other figure.
- [ ] The key result is visually loudest; context is muted.
- [ ] Axis labels have units; tick labels are readable at final size (7 to 9 pt).
- [ ] Error bars or bands are present where there is variance, and the caption says what they are (std, SE, 95% CI) and n.
- [ ] Baselines are shown and marked.
- [ ] No red-vs-green-only distinctions; the key condition still stands out in the greyscale preview.
- [ ] Conditions appear in argument order (baseline, alternatives, method).
- [ ] Legend is minimal, or replaced by direct labels.
- [ ] Exported as vector PDF with TrueType (Type 42) fonts, at final width.
- [ ] The caption states the takeaway, the figure plus caption stand alone, and the claim holds for every model and condition shown. Check the numbers before writing "far more" or "no cost".
- [ ] The script that generates it is saved next to the data, so it can be regenerated.
